# Add editor-sourced menu bar icon options

## Context

DefaultOpener (`~/Projects/defaultopener`) is a fork of apexskier/DefaultBrowser extended with
markdown-editor MRU selection (see `DefaultOpener/AppDelegate.swift`, `Defaults.swift`,
`ObsidianVault.swift`). Alongside the original browser MRU pool, it now has a parallel editor MRU
pool (`validEditors`, `runningEditors`, `getOpeningEditorId(forFile:)`) for opening `.md` files
with the most recently used markdown editor, with Obsidian special-cased and vault-gated.

The app has a menu bar status icon whose appearance is user-configurable via a popup in
Preferences ("General" area, `menuBarIconPopUp`). Today that popup offers exactly 4 options,
generated by `updateMenuBarIconPopUp()` in `AppDelegate.swift`: every combination of
`MenuBarIconStyle` (`.browserIcon` = plain icon-only, `.framed` = base icon framed with a small
overlay) crossed with adaptive/full-color (the `template` flag). Every code path involved
(`generateIcon` in `ImageTransforms.swift`, `getMenuBarIcon(for bundleId:)`, the popup preview
generation, and the live status-bar icon assignment in `updateMenuItems()`) is hardcoded to depict
the **browser**: `defaults.primaryBrowser` for the popup preview, `getOpeningBrowserId()` for the
live icon. There is no "source" (browser vs editor) dimension anywhere in this system today; it
was never designed for the editor pool to have its own icon representation.

## Goal

Add four new menu bar icon style options that depict the current markdown editor instead of the
current browser: "Full Color Editor Icon", "Full Color Framed Editor Icon", "Adaptive Editor
Icon", "Adaptive Framed Editor Icon" (naming can be adjusted for symmetry, see Open questions).
Selecting one of these should make both the Preferences popup preview and the live status-bar icon
depict the resolved editor's app icon instead of the resolved browser's.

## Requirements

1. Add a persisted preference for which source (Browser or Editor) the menu bar icon depicts,
   following the existing `ThisDefaults`/`DefaultKey` pattern in `Defaults.swift`. Must default to
   Browser, so existing installs and the existing 4 options behave exactly as they do today with
   no migration needed.
2. `updateMenuBarIconPopUp()` must emit 8 total items: the existing 4 (browser-sourced, unchanged
   behavior) plus 4 new editor-sourced ones, previewing with an editor bundle ID (e.g.
   `defaults.primaryEditor`, falling back to a sensible default editor bundle ID the way the
   browser side falls back to `"com.apple.Safari"`).
3. `MenuBarIconMenuItem` needs a new field (e.g. `source: MenuBarIconSource?`) alongside its
   existing `style`/`template` fields, so `menuBarIconPopupChange(sender:)` can read which source
   was picked and persist it.
4. `updateMenuItems()`'s live status-bar icon assignment (`button.image = getMenuBarIcon(for:
   openingBrowser) ...`) must branch on the persisted source preference: use
   `getOpeningBrowserId()` when source is Browser (unchanged), or a new file-independent editor
   resolution when source is Editor.
5. `getOpeningEditorId(forFile:)` cannot be reused directly for this, because it requires a
   specific file to decide Obsidian's vault eligibility. A new file-independent variant is needed
   for icon-preview and live-icon purposes: same MRU/primary/first-available resolution logic as
   `getOpeningEditorId(forFile:)`, but with Obsidian always excluded (equivalent to treating "no
   file" as "not in any vault, hence not eligible"). Do not attempt to invent or guess a file
   context for this; excluding Obsidian is the correct approach per the brainstorm that produced
   this prompt (see Open questions for the one part of this that wasn't fully settled).
6. `generateIcon`, `getMenuBarIcon(for bundleId:)`, and `IconCacheKey` are already fully generic
   (accept any bundle ID) and should not need changes; reuse them as-is for editor bundle IDs.

## Approach

Read `AppDelegate.swift`'s existing browser-side implementation first for the exact shape to
mirror: `updateMenuBarIconPopUp()` (~line 487), `MenuBarIconMenuItem` class (~line 70),
`menuBarIconPopupChange(sender:)` (~line 1638), and the live icon assignment inside
`updateMenuItems()` (~line 959-975). Also read `getOpeningEditorId(forFile:)` (~line 597) to
extract its MRU/primary/first-available logic into a shared private helper that both the
file-aware version (vault-checked) and the new file-independent version (Obsidian always
excluded) can call, rather than duplicating the MRU-walk twice.

## Out of scope

- Any change to the existing 4 browser-sourced options' behavior or persisted values (the
  `MenuBarIconStyle` enum's rawValues must not change, since `defaults.menuBarIconStyle` is already
  persisted on real installs).
- Any change to how `.md` files actually get opened (`openMarkdownFiles`, `getOpeningEditorId(forFile:)`
  itself); this prompt is purely about the menu bar icon's visual representation.
- Re-litigating the Obsidian vault-detection sandboxing fix or the App Sandbox removal already done
  on this fork; both are settled, unrelated context.

## Acceptance criteria

- Preferences popup shows 8 total menu bar icon style items, the original 4 unchanged plus 4 new
  editor-sourced ones with correct preview thumbnails built from the current primary/MRU editor's
  app icon.
- Selecting an editor-sourced option persists correctly across app relaunch and updates the live
  status-bar icon to depict the resolved editor (not the browser).
- Selecting a browser-sourced option continues to behave exactly as it does before this change.
- With an editor-sourced option selected, Obsidian is never depicted as the "current editor" icon
  even if it would otherwise win an MRU/primary resolution, since there is no file context to
  vault-check.
- Existing preference file on a real install (`~/Library/Preferences/com.marcbailey.defaultopener.plist`)
  continues to load without any manual migration step.

## Open questions

- Exact final title strings for the 8 popup items. Proposed: "Adaptive Editor Icon", "Full Color
  Editor Icon", "Adaptive Framed Editor Icon", "Full Color Framed Editor Icon" for the new ones.
  Whether to also rename the existing 4 browser-side titles for symmetry (e.g. "Browser Icon" to
  "Adaptive Browser Icon") is cosmetic only (persistence keys off the `MenuBarIconStyle` enum's
  rawValue, not the title text, so renaming is safe and needs no migration) but wasn't decided;
  confirm with Marc before renaming existing labels.
- Confirmed direction, stated for completeness rather than left open: Obsidian should never be
  depicted as the menu bar's "current editor" icon, since there's no file to vault-check against.
  This was the working assumption going into this prompt's write-up; revisit only if that
  assumption turns out to be wrong in practice.
